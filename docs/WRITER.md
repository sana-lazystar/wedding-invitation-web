# WRITER — 문서 문체 기준

이 문서는 이 레포의 공개 문서(README·원장·정책·명세 등 마크다운 전부)를 쓸 때 따르는 문체 기준입니다. 법적 텍스트에는 적용하지 않습니다. UI 화면 문구(버튼·에러·안내 등) 기준은 화면 문구가 생기면 `ontology/ux-writing.md`로 분리합니다. 그 전까지는 이 문서를 따릅니다.

기준의 출처는 토스가 공개한 테크니컬 라이팅 자료입니다.

- [토스 테크니컬 라이팅 가이드](https://technical-writing.dev/) ([원문 저장소](https://github.com/toss/technical-writing), CC BY-NC-SA 4.0)
- [토스의 8가지 라이팅 원칙](https://toss.tech/article/8-writing-principles-of-toss)

## 어미 — 합니다체

- 설명은 "~합니다 / ~입니다"로 씁니다.
- 지시는 "~하세요"로 씁니다.
- "~이다 / ~한다"체는 쓰지 않습니다.
- 과도한 경어는 쓰지 않습니다. "~하시겠어요?", "~하시기 바랍니다" 대신 "~하세요"를 씁니다.

## 문장 규칙 5가지

### 1. 짧게 씁니다

한 문장에는 생각 하나만 담습니다. "~하며, ~하고, ~합니다"처럼 이어지는 문장은 나눕니다.

- 나쁜 예: 버튼을 클릭하면 다음 단계로 이동하게 되며, 그 이후의 작업을 진행할 수 있습니다.
- 좋은 예: 버튼을 클릭하면 다음 단계로 이동합니다. 이동 후 이어서 작업하세요.

메타 담화도 지웁니다. "앞서 설명했듯이", "결론적으로", "아시다시피" 같은 표현은 핵심 정보가 아닙니다.

### 2. 구체적으로 씁니다

- 명사 대신 동사를 씁니다. "설정 변경을 수행합니다" → "설정을 바꿉니다".
- 모호한 표현을 피합니다. "영향을 받을 수도 있습니다" → "삭제됩니다". 확실한 정보만 씁니다.
- 누가, 무엇을, 어디서, 어떻게 하는지 생략하지 않습니다.
- 수치와 기준을 제시할 수 있으면 제시합니다.

### 3. 일관되게 씁니다

- 같은 개념은 문서 전체에서 같은 단어로 부릅니다.
- 기술 용어는 공식 표기를 따릅니다.
- 약어는 처음 나올 때 풀어 씁니다. 예: SSR(Server-Side Rendering).

### 4. 읽는 사람을 주체로 씁니다

- 문서를 읽는 사람이 행동의 주체입니다. "이 라이브러리는 초기화를 수행합니다" → "이 명령어를 실행하면 초기화할 수 있습니다".
- 능동형으로 씁니다. "설정이 완료되어야 합니다" → "설정을 완료하세요".
- 도구의 동작 자체를 설명할 때만 도구를 주어로 씁니다.

### 5. 자연스러운 한국어로 씁니다

- 빼도 뜻이 통하는 한자어는 뺍니다: 수행, 진행, 실시, 처리.
- 번역체를 고칩니다. "~을 통해" → "~로". 영어식 명사형 나열("인증 처리가 완료된 후 접속 설정 진행이 가능합니다")은 동사 중심으로 풉니다("인증한 후 접속을 설정할 수 있습니다").

## 구조 규칙

- **가치를 먼저 씁니다.** 기능 나열보다 "이 문서를 읽으면 무엇을 할 수 있는지"를 먼저 전달합니다.
- **제목은 30자 이내로, 핵심 키워드를 넣어** 씁니다. 물음표와 느낌표는 쓰지 않습니다. 같은 레벨의 제목끼리 스타일을 통일합니다.
- **새 개념은 나온 자리에서 한두 문장으로 정의합니다.**

## AI 티 제거 체크리스트

기계가 쓴 티가 나는 패턴입니다. 발견하면 고칩니다.

| 패턴 | 고치는 법 |
|---|---|
| 대시(—) 남발 | 문장을 나누거나 쉼표로 바꿉니다 |
| 콜론(:) 뒤 나열 강박 | 완결된 문장으로 풉니다 |
| 추상 은유 ("하중을 받는 구조물", "~은 연극이다") | 실제 뜻을 그대로 씁니다 |
| 선언체 연발 ("~이다. ~이다. ~이다.") | 합니다체 + 문장 구조를 다양하게 합니다 |
| 한 문장에 생각 3개 | 문장을 나눕니다 |
| 볼드 남발 | 문단에 하나 이하로 줄입니다 |
| 수동형 ("~로 만들어졌다") | 능동형으로 바꿉니다 |
| 문단이 전부 같은 길이·같은 구조 | 근거가 강한 항목은 길게, 약한 항목은 짧게 둡니다 |
| 문장마다 숫자 | 문단당 한두 개만 남기고 나머지는 문장이 지탱하게 합니다 |

## 구조 규칙 — 문장이 깨끗해도 걸리는 것

문장 규칙을 다 지켜도 구조가 반복되면 기계가 쓴 티가 납니다. 2026-08-14에 session-registration-system 레포의 리뷰 문서 3편을 감사하면서 확인했습니다. 문장 규칙은 대체로 지켰는데 대시 140개, 볼드 271개가 나왔고 절마다 선언문이 반복됐습니다.

- **선언문은 문서당 한 번만 씁니다.** 짧은 단정형 제목이나 문장이 절마다 반복되면 슬로건 모음이 됩니다.
- **"X가 아니라 Y" 대조도 문서당 한 번입니다.** 반복하면 수사 패턴이 드러납니다.
- **문단 템플릿을 반복하지 않습니다.** 모든 문단이 선언 한 줄에 근거 나열 구조이고 길이까지 비슷하면, 문장이 깨끗해도 나열로 읽힙니다. 문단 길이와 첫 문장 형태를 섞습니다.
- **문단 길이는 근거 강도에 비례하게 둡니다.** 할 말이 많은 항목은 길게 쓰고, 아닌 항목은 짧게 끝냅니다.
- **지도 문장을 쓰지 않습니다.** "아래에서 설명합니다", "먼저 말씀드리면"처럼 뒤에 나올 내용을 예고하지 않습니다. 본문이 직접 보여줍니다.
- **메타 선언을 쓰지 않습니다.** 문서가 자기 자신에 대해 말하지 않습니다. "정직하게 적겠습니다" 대신 근거와 한계를 그대로 씁니다.
- **장면을 연출하지 않습니다.** 비유는 개념을 처음 설명할 때 한 번만 쓰고, 그다음부터는 실제 이름으로 부릅니다.
- **문장 길이를 섞습니다.** 짧은 문장만 이어져도 균일한 리듬이라 기계 티가 납니다.
- **과잉 세정하지 않습니다.** "그래서", "~했더니" 같은 연결어까지 지우면 오히려 어색해집니다. "결론적으로", "앞서 설명했듯이" 같은 메타 담화는 그대로 금지입니다.

## 사실 규칙

- **검증되지 않은 수치는 쓰지 않습니다.** 숫자에는 출처가 있어야 합니다. 추정이면 추정이라고 밝힙니다.
- **숫자에 비교 기준선을 답니다.** "커버리지 76%"만으로는 판단할 수 없습니다. "레포 기준 76%, 회사 기준 65%"라고 쓰면 읽는 사람이 판단할 수 있습니다.
- **한계와 미검증을 최소 한 군데 남깁니다.** 전 항목이 확실한 문서는 사람이 쓴 글이 아닙니다.
- **고친 뒤 사실의 수위를 대조합니다.** 문체를 다듬다 보면 "이슈"가 "장애"로, "가능성"이 "확정"으로 조용히 올라갑니다. 원본과 맞춰봅니다.
- **같은 사례를 재탕하지 않습니다.** 대표 사례는 가장 강한 자리에 한 번 놓고, 다른 자리에서는 다른 사례를 씁니다.

### Before / After

| Before | After | 고친 것 |
|---|---|---|
| 곡선은 4에서 꺾이는데, 답은 5다 | 곡선은 4에서 꺾입니다. 그런데 4에서 멈추면 인프라만 보는 도구가 됩니다. | 선언형 대조를 설명으로 |
| org 레포가 도면, 코드가 건물, ontology가 실측반입니다 | ontology는 코드를 읽어 실제 구성을 기록합니다. | 연출을 실제 동작으로 |
| 결정론 추출 + LLM 검증 = 정밀도 높음, 재현율 미상 | 결정론으로 뽑고 LLM으로 검증하면 틀린 값은 걸러집니다. 빠뜨린 값은 못 걸러냅니다. | 콜론 나열을 문장으로 |
| 커버리지 76% | 레포 기준 76%입니다. 회사 기준으로는 65%가 자기 레포의 80% 이상을 커버받습니다. | 숫자에 기준선 |

## 영어 문서 규칙

한국어 규칙과 같은 원칙을 영어에 적용합니다.

- 짧은 문장. 한 문장에 생각 하나.
- 능동태. "is configured by" → "configures".
- 2인칭. 읽는 사람을 "you"로 부릅니다.
- 명사화 제거. "perform configuration" → "configure".
- 메타 담화와 수사적 표현 제거. "needless to say", "it is worth noting" 등.

## 검증

문서를 다 쓰면 확인하세요. 1~3번은 문장, 4~6번은 구조, 7~8번은 사실입니다.

1. 소리 내어 읽었을 때 사람이 말하는 것처럼 자연스러운가. 옆자리 동료에게 그대로 말한다고 상상해서 어색하면 고칩니다.
2. 어느 문장이든 반으로 자를 수 있는가. 자를 수 있으면 자릅니다.
3. AI 티 체크리스트의 패턴이 남아 있는가. 대시와 볼드는 세어봅니다.
4. 선언문이나 "X가 아니라 Y" 대조가 두 번 이상 나오는가.
5. 문단 길이가 부자연스럽게 균일하지 않은가.
6. 지도 문장이나 메타 선언이 남아 있는가.
7. 출처 없는 숫자가 있는가. 핵심 숫자에 비교 기준선이 있는가.
8. 한계나 미검증 항목이 최소 한 군데 있는가. 고치기 전 원본과 사실의 수위가 같은가.
