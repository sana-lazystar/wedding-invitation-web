# 디자인 시안 — 와이어프레임에서 화면으로

## 발단

스택·인프라 논의가 끝나고 코드 착수 전 단계입니다. 이산하가 와이어프레임(`docs/design/모바일청첩장_와이어프레임.pdf`, 14블록)과 커버용 일러스트 2장(`docs/design/scene1/`)을 준비했고, 사진 원본 20장이 `docs/gallery/`에 있습니다. 이산하는 Claude Design으로 시안을 만들고, Claude는 시안을 레포에 정리하고 Artifact로 발행해 폰에서 확인할 수 있게 하는 흐름을 원합니다. 이 논의는 그 흐름과 저장 구조를 정합니다. 와이어프레임이 "청첩장에 무엇이 들어가는가"를 이미 답하므로, 요구 정의 논의를 따로 열지 않고 이 논의에서 요구 원장을 함께 채웁니다.

### 2026-09-06 18:28:14 · Claude (T2)

- 읽은 것. 와이어프레임 16쪽 전부, 커버 일러스트 2장(860×1428 신랑신부 컷아웃 PNG, 860×1829 커티지홀 아치 배경), `docs/ontology/README.md` §서랍 정의의 `ia/` 행, README §논의의 `artifacts/` 점검 규칙, DesignSync 도구 명세.
- 와이어프레임 요지. 단일 페이지 14블록 약 14.8화면. 커버·핵심 정보·마지막은 1화면 고정이고 사이는 자유 흐름이다. 하단 고정 바에 오시는 길·연락처 버튼이 상시 노출된다. 3~8번 블록만 캐릭터(토끼 = 신부, 메모지 왼쪽 · 수달 = 신랑, 오른쪽)가 등장하고, 이야기 구간은 요체·초대 이후는 격식체다. 레이아웃 규칙은 배경 위 종이, 종이 위 사진·글, 그 위 오브제(종이 밖으로 걸침), 본문 한 줄 약 22자·줄 간격 1.7배, 메모지 안쪽 여백 좌우 16·위아래 20이다. 블록은 1 커버, 2 핵심 정보(아치), 3 인사, 4 Part 1 신랑, 5 Part 1 신부, 6 Part 2 신랑, 7 Part 2 신부, 8 Part 3, 9 초대(편지지), 10 만화 + 갤러리(9장 + "+31" 타일, 전체화면 뷰어), 11 오시는 길(약도·주차·지하철·버스), 12 하객 안내, 13 마음 전하는 곳(계좌 6개, 행 전체 복사), 14 마지막(커버 아치 축소)이다.
- 판단 1, 단위. IA 단위는 URL이 아니라 블록이다. URL은 `/` 하나이고 갤러리 뷰어도 같은 URL 위의 오버레이다. "URL 1개 = 파일 1개" 원칙은 유지하되 지금은 파일이 하나씩이다. 블록마다 앵커 id를 두어 명세·시안·코드가 같은 이름으로 블록을 부른다.
- 판단 2, 세 자리. ① 명세는 `docs/ontology/ia/`에 둔다(텍스트 정본, `/` = `index.md`, 라우트 표는 `README.md`). 와이어프레임 PDF는 git 제외 폴더에 있으니 `index.md`가 그 git 정본이 된다. ② HTML 시안은 `docs/artifacts/`에 URL 경로를 그대로 미러한다(`/` = `index.html`). ontology는 살아있는 정본 텍스트만 두는 서랍이고 HTML 시안은 코드가 생기면 스냅샷이 되므로 ontology 밖이 맞다. README §논의가 `artifacts/`를 "살아있는 데모"로 이미 예약했고 `check-refs.mjs`가 `docs/artifacts/README.md`를 스캔 대상에 넣어 두었다. ③ 라운드 비교가 필요한 시점의 사본은 `docs/ontology/references/YYYY-MM-DD--design-round-N.html`로 동결한다.
- 판단 3, 확인 방식. Artifact 샌드박스는 외부 이미지·CSS 로딩을 막으므로 발행본은 이미지를 data URI로 인라인해야 한다. 원본 HTML(`docs/artifacts/index.html`)은 상대 경로로 이미지를 참조하고, 발행 직전 스크립트(`docs/scripts/inline-artifact.mjs`, 스택 결정 10)가 이미지를 웹 크기로 줄여 인라인한 사본을 스크래치패드에 만든다. 같은 파일을 같은 Artifact에 재발행하니 링크는 하나로 고정되고 버전 라벨로 라운드를 구분한다. 발행 한도는 16MB다.
- 판단 4, 흐름. 한 라운드는 ① 이산하가 Claude Design에서 블록 몇 개를 만들어 HTML을 내보낸다 ② Claude가 `docs/artifacts/index.html`에 합치고 인라인 사본을 Artifact로 재발행해 링크를 준다 ③ 이산하가 폰에서 보고 피드백한다 ④ Claude가 피드백과 결정(키 컬러·폰트·질감 등)을 이 논의록에 적고 `ia/index.md`를 갱신한다. DesignSync 도구는 Claude Design의 "디자인 시스템" 타입 프로젝트만 읽고 쓴다. 이산하의 프로젝트가 그 타입이면 Claude가 파일을 직접 끌어오고, 아니면 내보낸 파일을 이산하가 `docs/artifacts/`에 넣는다.
- 판단 5, 개인정보. 와이어프레임 13번의 계좌 6개와 양가 부모님 성함은 사이트에 실리므로 스택 결정 14의 허용 범위 안이다. 그래도 시안·명세에는 와이어프레임처럼 자리표시(`000-0000-0000`, `이OO`)만 두고, 실값을 넣는 시점·방식은 따로 결정한다(Q10).
- 와이어프레임 16쪽 "남은 작업"에서 원장으로 옮길 것. 요구 후보 5건(검색엔진 차단 noindex · 카카오톡 공유 미리보기 이미지·캐시 사전 테스트 · 라이트 모드 고정 · 어른 하객 가독성(얇은 폰트·옅은 회색 금지) · 이미지 용량 최적화)은 구조 확정 뒤 REQ로 등재한다. 미확정 6건은 지금 원장에 올렸다. Q8 키 컬러·포인트 컬러·종이 질감 강도, Q9 캐릭터 표정 세트, Q10 계좌·성함 실값 반영 시점·방식, U-5 신부대기실 정리 시각, U-6 하객 대기 공간·식사 방식, U-7 예식 당일 연락처 담당.
- 다음. 결정 1~6이 확정되면 `docs/ontology/ia/README.md`·`index.md`(와이어프레임 전사 + 앵커 id), `docs/artifacts/README.md`, 인라인 스크립트를 만들고 REQ 5건을 등재한다. 시안 HTML 첫 파일은 Claude Design 산출물이 오면 만든다.
